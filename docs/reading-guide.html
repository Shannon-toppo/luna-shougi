00

全体像 ── エンジンは「探索 × 評価」の掛け算

まずこの1行だけ覚えれば、以降の用語はすべてどちらかの側に置ける。

将棋エンジンは、突きつめると2つの部品しかない。

  • 探索（search） ── 「この手を指したら、次はこう、その次はこう」と先を読む部分。読む局面の数が勝負。
  • 評価関数（evaluation） ── 読んだ先の局面を見て「この局面は先手が+300点くらい良い」と1つの数字を返す部分。先は読まない。盤面を見た瞬間の点数だけを答える。

探索は評価関数を何百万回も呼ぶ。だから強さは「どれだけ深く読めるか」と「読んだ先を正しく採点できるか」の掛け算になる。この事業（フェーズ5以降）でやっているのは、後者を手書きのルールからニューラルネットに置き換えることで、それがNNUEである。

この文書の読み方

01〜06 は用語集。07 は「実際に何が起きたか」の年代記で、ここを読むと用語が数字と結びつく。意思決定に必要なのは 07・08・09 の3つで、01〜06 はそこを読むための語彙。

01

将棋エンジンの土台

フェーズ0〜2で作った部分。もう完成していて、いま議論の対象にはならないが、語彙としては全編に出てくる。

USIUniversal Shogi Interface

エンジンとGUIの間の共通語。標準入出力でテキストをやり取りするだけの単純なプロトコルで、position（局面を教える）、go（考えろ）、bestmove（指し手を返す）、setoption（設定を変える）が主要な命令。USIさえ喋れば ShogiGUI（Windows）でも ShogiHome（Mac）でも動くので、GUIごとの対応は不要。

SFEN局面の文字列表現

盤面・持ち駒・手番・手数を1行の文字列で表したもの。チェスのFENの将棋版。data/*.sfen は教師データと同じ局面をこの形式で並べたファイルで、Python側の計算結果をC++エンジンに投げ返して突き合わせるときに使う。

合法手生成move generation

その局面で指せる手を全部列挙する処理。将棋では二歩・打ち歩詰め・行きどころのない駒・王手放置など除外ルールが多く、プロジェクト中で最もバグが出やすい場所とされている（PLAN.md フェーズ1）。

perftperformance test

「初期局面からN手すべて指し尽くすと、末端に何通りの局面があるか」を数えるテスト。公開されている正解値と1ノードでも違えば合法手生成にバグがある。正しさを機械的に保証できる数少ない手段。

Zobristハッシュ局面の64bit指紋

盤面＋持ち駒＋手番から一意な64ビットの値を作る手法。駒を1つ動かすたびに乱数をXORするだけで更新できるのが利点。置換表の鍵と千日手判定、そしてNNUEの差分計算の検証（後述）に使われる。

局面 / 指し手 / 手番position / move / side to move

「局面」は盤の状態一式。「手番」はいま指す側。この事業で重要なのは、点数は常に「手番側から見て」表すという約束（手番視点）。先手が+300良い局面でも、後手番なら評価は −300 と返る。

02

探索 ── 読む側の語彙

フェーズ3と6。すでに +456 Elo と +173 Elo を出して完成している。NNUEの話にも「探索が実際に評価する局面」という形で常に出てくる。

alpha-beta 探索αβ枝刈り

全部読むのをやめる基本技法。「相手がこの手を選ぶ以上、こちら側の残りは読んでも結論が変わらない」枝を切る。結論は全部読んだ場合と完全に一致する（＝安全な枝刈り）。

反復深化iterative deepening

深さ1で読む → 深さ2で読む → 深さ3…と、浅い探索から順にやり直す。無駄に見えるが、浅い探索の結果で手の順番を良くできるので、いきなり深く読むより速い。時間切れになっても直前の深さの答えが残るのも利点。

静止探索quiescence search

規定の深さに達しても、取り合いの途中なら取り合いだけ最後まで読み切る延長。これがないと「飛車を取った直後」で読みを止めて大喜びしてしまう（水平線効果）。この事業で「消費者」と呼ばれるのはこの部分。教師データとの分布のずれは、ここで起きていた（07参照）。

stand-pat静止探索の据え置き値

静止探索で「何も取らずにこのままでいい」と判断するときの基準値で、そこで呼ばれる静的評価そのもの。探索木ダンプで「standpat 78% / prune 22%」と出るのは、評価が呼ばれた場所の内訳。評価関数の顧客はほぼここだと考えてよい。

置換表transposition table / TT

「この局面はもう調べた、結果はこれ」を記憶する巨大なハッシュ表。将棋は手順前後で同じ局面に到達することが多いので効果が大きい。既定64MB、USIオプション USI_Hash で変える。Lazy SMP で全スレッドが共有する唯一のもの。

ムーブオーダリングMVV-LVA / killer / history

良さそうな手から先に読む工夫。αβは「良い手を先に読むほど切れる枝が増える」性質があるので、順番が速度を決める。MVV-LVA＝安い駒で高い駒を取る手を優先、killer＝同じ深さで前に切れた手、history＝過去によく効いた手。

枝刈り一式null move / LMR / futility / LMP / PVS

αβと違い、間違えることがある省略。間違えると壊れるのが「正しさ」ではなく「強さ」なので、採用基準は理屈ではなく自己対局の勝率になる。

null move＝相手にタダで1手渡してもまだ勝っているなら読むまでもない。futility＝静的評価がαから大きく離れていて、駒を取らない手では埋まらない差なら読まない。LMR＝手の順番で後ろのほうは浅く読み、良さそうならその分読み直す。PVS＝最善手はもう見つかっている前提でゼロ幅で確認する。

フェーズ6でこの一式を入れた効果が +456 Elo。深さ6のノード数が6100万から15万になった（413分の1）。

SEEStatic Exchange Evaluation / 静的交換評価

ある升で取り合いが起きたとき、探索せずに最終的な損得を数える近似計算。「SEEが負になる取りは読まない」が静止探索の爆発を止めた最大の要因。持ち駒が多い局面では、損な取り合いを始める手が持ち駒の数だけ存在するため。

delta pruning静止探索の足切り

その手で取れる駒＋成りの得を全部足してもαに届かないなら読まない。余裕（マージン）は歩1枚ぶん。

Lazy SMP怠惰な並列探索

全スレッドが同じ局面を最初から最後まで各自で探索するだけの並列化。木を分割して配らない。共有するのは置換表だけで、誰かが早く証明したことがそこに載って他が得をする。設計としては雑だが、コード量が桁違いに少なく競合バグが入りにくい。8スレッドで +173 Elo。

ノード / nps / seldepth探索の単位

ノード＝探索が訪れた局面の数。nps＝1秒あたりのノード数（速度）。seldepth＝実際に到達した最大の深さ（静止探索の延長を含む）。枝刈りを入れると nps は落ちてノード数が激減するのが正常で、フェーズ6では nps 150万→85万、ノード数413分の1。

固定深さ / 固定時間測定条件

固定深さ＝「必ず深さ6まで読む」。評価関数の質だけを比べたいときに使う。評価が重くて遅くなっても、読む量が同じなので不利にならない。

固定時間（--movetime 200）＝「1手200ms」。実戦に近く、評価が遅いことのペナルティが乗る。NNUEは手書きよりノードが1.8倍必要で NPS 0.58倍なので、固定時間に切り替えると数字は今より悪くなる。いまの世代比較は全部固定深さで測っている。

03

評価関数と点数の単位

「点数」がいくつも違う単位で出てくるのがこのプロジェクトの読みにくさの主因。ここだけは丁寧に。

手書き評価hand-written / handmade

フェーズ4で作った、人間がルールを書いた評価関数。駒割（どの駒が何点か）＋PST＋玉の安全度＋持ち駒ボーナス＋手番ボーナス。いまだにNNUEより強く、打倒対象であり、同時に教師データのラベルを付ける先生でもある。

駒割 / PSTmaterial / piece-square table

駒割＝駒の種類ごとの固定点数の合計。PST＝「同じ金でも5九にいるのと5五にいるのでは価値が違う」を81マス分の表で表したもの。手書き評価はこの2つが本体。

エンジンの点数単位歩 = 90

このエンジンでは歩1枚が90点。だから「残差300点」は歩3枚強の誤差という意味。詰みは ±32000付近の特別な値（詰みスコア）で表す。

ポナンザ定数600

点数を勝率に換算するときの尺度。勝率 = sigmoid(score / 600)。600点差でだいたい勝率73%、という換算式の「600」がこれ。ネットワークが学習しているのは「点数÷600」に相当する量で、出力を16で割るとエンジンの点数になる。

この定数を1200や1800に上げると、ネットが大きい点数を出せる余地が広がる。実際に試して、盤上で3組ともはっきり負けた（LOS 100%）。シグモイドを引き伸ばすと決着帯の分解能が犠牲になり、そちらの損が重い。600のまま確定。

勝率空間 / 点数空間損失をどこで測るか

勝率空間＝点数をsigmoidで0〜1に潰してから誤差を測る。+2000と+3000は指し手としてほぼ同じなので、その差を学習させて容量を無駄にしないための設計。これが最初の3世代の損失。

点数空間＝点数そのもので誤差を測る。勝率空間では3300点より上の勾配がほぼ0になるので、ネットが大きい点数を出す動機を失う。gen4で足したHuber項はこちら側から尾部に圧力をかけるもの（05参照）。

negamax と定数ずれなぜ「平均のずれ」だけが危険か

評価は手番視点なので、探索は1手ごとに符号を反転させながら値を積む（negamax）。ここで評価関数に一定のオフセットが乗っていると、木の全ノードに撒かれた手番ボーナスとして効き、指し手が変わる。ばらつき（sd）は平均されて消えるが、平均のずれは消えない。gen1では −34.6点のずれを取り除いただけで +62 Elo あった。およそ1点 ≒ 1.8 Eloという換算はここから来ている。

04

NNUE本体

ネットワークの形と、それをCPUで速く動かすための仕掛け。

NNUEEfficiently Updatable Neural Network

「効率的に更新できるニューラルネット」。GPUではなくCPUで、探索の中から何百万回も呼ばれることを前提に設計された評価関数。名前の「更新できる」が本質で、下の差分計算のこと。

HalfKP特徴量の設計

入力の作り方。「自玉のマス」×「玉以外の駒がどこにあるか」の組を1つの特徴とする。K＝King（玉）、P＝Piece。「Half」は自玉基準と相手玉基準で2セット作るから。

玉の位置ごとに別の特徴になるので、「玉が6八にいるときの、相手の桂が7七にいることの意味」を個別に学習できる。これがHalfKPが効く理由。

BonaPiece1548種の駒表現

「どの種類の駒が、どこにあるか」を通し番号にしたもの。盤上の駒は種類ごとに81マス分、持ち駒は1枚ごとに1スロット。玉は含まない（取られないし、位置はもうKの側に入っている）。結果、どの局面でも立つ特徴はちょうど38個（40枚 − 玉2枚）。駒を取っても盤から持ち駒に移るだけなので数は変わらない。

ネットワークの形HalfKP → 256×2 → 512 → 32 → 32 → 1

入力次元は 81 × 1548 = 125,388。これを256次元に落とす層（特徴変換器）を自玉基準・相手玉基準の2本持ち、繋げて512次元。以降 32 → 32 → 1 と小さくして、最後に1つの点数を出す。

512次元の前半が手番側、後半が相手側。これがネットワークに手番を伝える唯一の経路なので、C++とPythonで順序が食い違うと静かに壊れる。

特徴変換器の重みだけで 125,388 × 256 × 2バイト ≒ 64MB。.nnue ファイルのサイズはほぼこれ。

アキュムレータ / 差分計算incremental update

NNUEが速い理由。1手指しても立っている特徴は2〜3個しか変わらないので、38行を足し直す代わりに数行の加減算で済む。この「途中結果」を持っておく配列がアキュムレータ。

実装上の要点2つ。Zobristキーで検証するので、手を戻して別の手を指しても古いエントリは必ず弾かれる（探索側に約束事が要らない）。そして玉が動いたときはその側を作り直す ── HalfKPの特徴は全部玉のマスで索引されているため差分では済まない。

量子化quantization ── float → int

学習はfloat、対局は整数。速度のために整数演算にするが、両者が完全に一致していないと「学習中に測った強さ」と「実際に指すネットの強さ」が別物になる。

特徴変換器は int16（スケール127）、L1・L2は int8（スケール64）、出力層はスケール 9600/127。int8にスケール64だと表せるのは ±1.98 までなので、学習中に毎ステップ重みをクリップする（学習後にやると覚えたことが失われる）。

丸め誤差の定数化とバイアス補正この事業で最初に見つかったバグ

重み1個の丸めに偏りはない。しかしL1・L2は密で、どの局面でも全入力を使う。だから丸め誤差は「局面によってほとんど動かない活性ベクトル」に対する固定の線形汎関数、つまりほぼ定数になる。特徴変換器はこうならない（局面ごとに違う38行を足すのでノイズとして均される）。

そして 03 のとおり、定数は評価関数にとって一番まずい形の誤差。対策は測って引くこと ── 数千局面をfloatモデルと量子化ネットの両方に通し、各層の平均誤差をその層の整数バイアスから引く。バイアスはint32で桁が余っているので無料。gen1でこれを直して +62 Elo。エンジンのコードは1行も変わっていない。

SIMD / AVX2 / NEON推論カーネル

1命令で複数の数値をまとめて計算する仕組み。Windows（x86）は AVX2、Mac（arm64）は NEON。eval コマンドで (avx2) と出れば有効、(scalar) なら有効になっていない。CIはmacOSジョブでNEONカーネルを検証している（開発機がx86なので、NEONの自動テストはこれだけ）。

verify / drift2つのゲート

training/verify.py ── 同じ局面をPythonの整数演算とC++の整数演算に通し、点数が完全一致することを見る。近い、ではなく一致。両方とも整数なので、正当に丸めが違う余地はない。ただしこれは量子化後どうしの比較で、同じ偏りが両側に入っていれば「完全一致」と出る。

training/drift.py ── 元のfloatモデルと量子化ネットの差を測る。整数にする以上ずれるので完全一致では測れず、見るのは平均だけ。sdが数十点あるのは int8 が仕事をしているだけで正常。現行の閾値は ±20点（≒36 Elo）、測る局面は探索木6000局面。

05

学習パイプライン

教師データの作り方と、いま「つまみ」と呼ばれているハイパーパラメータ。08の意思決定はここの語彙で書かれている。

教師データ

教師データ / ラベル.bin ── 84 byte / 局面

「この局面の正解はこの点数」の組。作り方は luna-datagen でエンジンに自己対局させ、各局面で深さNの探索が出した点数を正解として記録する。加えてその対局の最終的な勝敗も一緒に入る。

1サンプル84バイト固定長。これのおかげでN番目へのシークが掛け算1回になり、止めた学習を「データのどこまで読んだか」まで含めて再開できる。

蒸留distillation ── この構図の名前

「先生（深い探索＋手書き評価）の答えを、生徒（ネットワーク）に真似させる」構図。先生の間違いも一緒に覚えるのが弱点。深さ4で作ったgen1が失敗したのは、深さ4の探索スコアが「手書き評価をそのまま4手伝播させたもの」でしかなく、劣化コピーにしかならなかったから。

--depth / --nodes教師の質と生成速度

ラベルを付けるときの探索の深さと、1手あたりのノード数上限（先に来たほうで打ち切る）。深いほど教師の質は上がるが、指数的に遅くなる。

深さ生成速度1000万局面あたり

60.54 M局面/時約19時間
80.13 M局面/時約77時間
--score-limit検閲 ── 3世代を負けさせた既定値

「点数がこの値を超える局面は教師に記録しない」上限。既定 3000。狙いは「もう決着している局面は静的評価の教師として意味が薄く、出力レンジを引っ張るだけ」。

そのとおりになった ── 引っ張られなかったので、ネットの出力がそこで止まった。gen2の教師の最大ラベルは2998で、gen2が出せる最大点数は2634。ところが探索が実際に評価する局面の37.5%は|score| 3000以上にあり、そこでの残差は手書き評価の3.3〜4.7倍。この文書群で「検閲（censored）」と呼ばれるのはこの現象。

ホールドアウトholdout ── 未知の局面

学習に使わず、汎化を測るためだけに取っておくデータ。1つのファイルを分割してはいけない ── 自己対局の連続する局面は同じ対局の似た局面なので、分割すると同じ対局が両側に入る。--seed を変えた別実行で作る。そして規律4のとおり、datagenの既定値で作ってはいけない（教師と同じ検閲を受け継いでしまう）。

探索木ダンプ / 混合treedump / tree mix ── 最大の効果

教師と消費者がずれていたという発見への対処。教師は「対局に現れた局面」、消費者は「静止探索のstand-patが評価する局面」で、両者の点数分布はまったく違う（教師の40%が|score|600未満、探索木では18%）。

そこで training/treedump.py で探索が実際に歩いた局面を採取し、教師データの一部をそれで置き換える。比率30%が最良（0%と100%はどちらも負ける ── 探索木の局面は教師の補正であって代替ではない）。

いま「つまみ」と呼ばれているもの

ハイパーパラメータ＝学習の設定値。この事業では4本を総当たりして、4本ともnullか負けだった（08で効いてくる事実）。

--lambda-score既定 0.7 効果なし

目標を「探索スコア」と「実際の勝敗」のどちらに寄せるか。1.0でスコアのみ、0.0で勝敗のみ。0.7でも1.0でも盤上は同じ（+0.7 ± 21.4）と測定済み。「ここにEloは無い」。教師超えを狙う段階になったら下げる検討をする、という位置づけ。

--score-weightHuber項の重み gen4で+313 Elo

この事業で最初に針を動かしたもの。勝率空間の二乗誤差とは別に、点数そのものへのHuber項を損失に足す。Huber損失＝小さい誤差は二乗、大きい誤差は絶対値で測る損失関数（外れ値に引っ張られにくい）。

loss = mean((sigmoid(pred) − target)²) + w × huber(pred, clamp(score, ±16000)/600)

ポナンザ定数を上げずに尾部だけに圧力をかけられるのが利点。0.03 → 0.3 で効き続け、1.0 で平ら。0.003のような小さすぎる値は0より悪い（尾部を動かすには足りず決着帯だけ汚す）ので、単調ではない。

混合比30% +196 Elo

教師のうち探索木由来の局面の割合。30%が最良で、100%は30%に363 Elo負ける。0%との差は総数によって ±25 〜 +196 まで動き、単調でもない。

ステップ / エポック / バッチ / lr学習の実行単位

バッチ＝一度に処理する局面数（既定8192）。ステップ＝重みを1回更新すること。エポック＝データを1周すること。lr＝学習率（既定1e-3）。フルスケール1421万局面で100,000ステップ＝57エポック、RTX 4070 Ti で 32分。学習は安い。高いのはデータ生成のほう（24時間）。

チェックポイントと再開bit-exact resume

学習を任意のタイミングで止め、続きから再開すると止めずに回した場合とビット単位で同じ重みになる。重みだけでなくオプティマイザの状態・データの読み位置・乱数状態まで保存している。1個385MB（重み128MB + Adamの状態256MB）。

SparseAdam / EmbeddingBag疎な勾配

特徴変換器は1局面につき38行しか触らないので勾配が疎。密な勾配にすると「数千個の数字を変えるために毎ステップ3200万個の重みを書き直す」ことになる。実測で17倍の差。

06

測るための言葉

この事業で最も高くついた学習は「何を物差しにするか」だった。指標を4つ作って4つとも外し、5回目でようやく当たっている。

盤上の指標（信頼できる）

Eloレート差

勝率をレート差に換算したもの。目安：+100 Eloで勝率64%、+200で76%、+400で91%。この事業の感覚値としては、+25は「小さいが本物」、+150〜200は「大きい」、+456（フェーズ6の枝刈り）は「桁違い」。

信頼区間（±）誤差幅

Elo +195.5 +/- 39.8 (95%) の後半。レート差がこの幅より小さければ、その変更は測れていない（勝ったように見えるだけ）。誤差幅は対局数の平方根でしか縮まない ── 100局で±75なら、±25にするには900局要る。1000局で概ね ±21〜25。

LOSLikelihood of Superiority

「本当に強くなっている確率」。95%を超えるまで採用の判断をしないのが規則。

直接対決 vs 対手書き勝率物差しが壊れていた話 要注意

この事業で最も重要な方法論上の発見。世代Aと世代Bを比べるのに、それぞれの「対手書き評価の勝率」を比べるやり方をずっと使っていた。

gen4以降の帯域では、この測り方が世代間の差を3〜5倍に潰す。実際に121 Eloの改善が「p=0.90（差なし）」として出た。原因は、両者が共通の相手（手書き評価）に大きく負けている領域では勝率の差が圧縮されるため。

いまは「直前の世代との直接対決1000局」で測る。対手書き勝率は目標の指標（50%を目指す）であって、比較の道具ではない。この発見で過去の判定が1つ撤回されている（gen5は「差なし」ではなく +164.5 Elo だった）。

luna-match の前提測定条件

開始局面は平手からランダム4手進めた局面（決定的なエンジン同士だと毎回同じ棋譜になるため）。同じ開始局面を先後入れ替えて2局指して有利不利を相殺する。千日手は4回目の同一局面で引き分け、連続王手の千日手は掛けた側の負け、入玉宣言は27点法で検証、320手で引き分け打ち切り。審判にエンジン本体の合法手生成をそのまま使っているので、ルール判定が食い違わない。

残差の指標（参考にしかならない）

残差sdresid ── 予測とラベルのずれ

「ネットが出した点数 − 正解ラベル」の標準偏差を、エンジンの単位（歩=90）で表したもの。小さいほど正確。外部の基準（手書き評価の残差）と比べられる唯一の数字。

決着帯 / 尾部 / 詰み帯deciding / tail / mate

局面を正解ラベルの大きさで3つに切る、この事業の共通語彙。

  • 決着帯（resid deciding）＝ |label| < 600。まだ勝負がついていない、指し手が最も変わりやすい帯。
  • 尾部（tail out）＝ |label| ≥ 3000 の局面で実際に出した点数の中央値。「大きい点数を出せるか（＝出力レンジ）」を見る。
  • 詰み帯＝ |label| ≥ 31000。ここは全評価が同じように駄目で、静的評価に±32000を期待するほうが間違い。だから指標からは除く。
合格基準詰みを除いた、探索木上の残差sd

いま採用されている唯一の残差指標。採用の条件は「gen1（1-399-0）とgen2（4-394-2）の両方を説明できること」で、これを満たしたのは6通りの読み方のうち1つだけだった（手書き818 / gen1 2593 / gen2 2423 ── 盤上のElo −800 と −759 と同じ形）。

ただし gen10 で天井に来た。gen10は全列で gen7 より悪い数字を出しながら、盤上では gen7 に勝っている。

訓練loss / val loss合格判定に使えない

訓練lossは学習が成功したかを何も言わない。gen1は訓練lossが1000分の1まで落ちて、対局では399/400負けた。

val loss（未知の局面での同じ損失）も、世代間では比較できない ── --score-weight を入れた世代は損失に項が1つ多いため。比較していいのは残差と盤上だけ。

足切りであって合格証ではない残差指標の位置づけ

この事業で確立した読み方。ここで手書き評価に負けるネットは盤上でも負ける（gen1で確認）。ここで勝っても盤上で勝つとは限らない（gen2で確認）。つまり「19時間を捨てずに済む」ための足切りとしてだけ裏付けがある。

ここが本題。現在地は対手書き 27.4%、目標50%まで 169 Elo。

状況を3行で

  • つまみは尽きた。点数項 0.3→1.0（−9.0）、混合比 30→100%（−363）、30→0%（+25）、lambda 0.7→1.0（+0.7）── 4本ともnullか負け。gen7のレシピは試した範囲で局所最適。
  • ループは回る。ただし薄い。「最新世代の探索から木を採り直して学習し直す」を1回転させて +29.3 Elo / 24時間。元の混合が同じ24時間で +145〜196 だったのに対し5〜7分の1。

「ループが薄くなる」の理由

混合が効いた理由には2つの説があった。(a) 尾部の供給（探索木は大きい点数の局面を多く含む）と、(b) 消費者との分布の一致（ネット自身が歩く局面で学ぶ）。gen10の実験は両者に逆の予測をさせる設計だった。

結果は +29。両方とも部分的に正しい ── 元の +145〜196 の大半は gen4 の極端な木が供給した尾部で、分布の一致そのものが上乗せするのは +29 分でしかなかった。gen7の探索はgen4の6割弱のノードで済むほど穏やかになっていて、供給するものが減っている。

決めることは実質3つ

  1. 50%というゲートを維持するか。これは「教師データを自前のネットで作るモード（--eval-file）に切り替えていいか」の線引き。負けている評価でラベルを付けると gen1 の構図に戻る、という理由で引かれている。維持するなら、それまでの手段はAとBとDに限られる。

  3. いつ持ち時間対局に切り替えるか。いまの数字は全部固定深さのもの。NNUEは NPS 0.58倍・ノード数1.8倍なので、実戦条件に移すと数字は下がる。切り替えのタイミングで枝刈りマージンの再調整（D）が必要になる。
意思決定に使える換算表

1点 ≒ 1.8 Elo（gen1で34.6点の定数除去が +62 Elo）。1000局の誤差幅 ≒ ±21〜25 Elo。つまり +25未満の改善は1000局では見えない。学習は32分、ラベル付けは24時間 ── 高いのは常にデータ生成のほうで、レシピを変えるだけの実験は安い。

規律7カ条

全部、失敗して払った代金と引き換えに書かれている。新しい実験を提案するときはこれに照らす。

  1. 判定は盤上のみ。残差指標は、gen1・gen2・gen4 の3点を説明できるもの（いまは詰みを除いた探索木残差sd）だけを参考に使う。
  2. 対局の前に drift と verify。量子化のバグはクラッシュしない。少し弱くなるだけで、学習側からもエンジン側からも単独では気づけない。
  3. info string eval nnue の確認。50%近い結果が出たらまず読み込み失敗を疑う ── 失敗したエンジンは手書き評価のまま対局を続けるので、失敗した測定は「勝率50%・有意差なし」という無害な顔で返ってくる。実際にこれで400局を無駄にした記録がある。
  4. ホールドアウトはdatagen既定値で作らない。教師と同じ検閲を受け継ぐ。探索木ダンプを使う。driftも同じで、探索木6000局面で回す。
  5. 世代間の比較は直前の世代との直接対決で測る。対手書き勝率は目標の指標であって、比較の道具ではない。gen4以降の帯域では差が3〜5倍に潰れ、121 Eloの改善が「p=0.90」として出た。
  6. 合格ラインを「既存の区間の外」で書かない。新しい側の不確かさを数えない検定になる。二標本で比べるか、直接対決で測る。
  7. 量子化の書き出しと drift の手続きを先に固定する。補正元は「学習ファイルに探索木の行があればその行、無ければファイル全体」を65,536局面。測定を見てから選ばない（過去に1回、測定集合に自由度を合わせてしまった）。閾値は ±20点（≒36 Elo）。この幅より小さい差を直接対決で主張するときは、両者の定数ずれを引き比べること。
実験設計の作法（明文化されていないが一貫している）

変数は1度に1つ。gen4は「変えたのはコマンドラインのフラグ1つ」、gen10は「変数は『どちらの探索が歩いた木か』だけ」と明記されている。

対照は「既存のもの」ではなく「同じ条件で作り直したもの」。深さ8の実験では、対照に既存の深さ6ラベルではなく同じ局面の深さ6付け直しを使っている（自己対局は置換表を1局持ち越すので、同じ深さでも付け直しと一致しない）。

予測を先に書く。gen10では2つの仮説が逆の予測をすることを事前に文書化してから測っている。

1つのファイルを分割してホールドアウトにすると、自己対局の連続局面が両側に入る。対策：--seed を変えた別実行で作る。

05検証lossは学習と同じ目標で測る

違う目標で測ると訓練lossと直接比較できず、過学習の判断ができない。

06go の直後に quit を送ると探索が中断される

スクリプトから点数を取ろうとして、探索が終わる前にプロセスを閉じてしまう。

07混ぜる比率を計算していなかった

データを混ぜる実験で、実際の構成比を数えずに進めた。対策：混合比は先に数字で決めて、総数を固定する。

08ラベルの付け直しは自己対局のラベルと一致しない

自己対局は置換表を1局持ち越すので、同じ深さで付け直しても同じ点数にならない。対策：対照は必ず「同じ手続きで付け直したもの」にする。

09検閲されたホールドアウトは検閲を報告しない

教師と同じ既定値で作ったホールドアウトは同じ帯域を欠く。存在しない帯域は、どう切り直しても見えない。3世代ぶんの誤診の根本原因。

10baseline.py の帯域表は「局面数、残差」の順である

列の順を取り違えて、局面数4197を残差sdとして読んでいた（実際の残差sdは10239）。文書に誤った数字が入り、後から訂正された。

11drift.py の平均は、測る局面集合で10点動く

閾値が8点だったので、集合を変えるだけで合否がひっくり返った。対策：測る集合を固定（探索木6000局面）し、閾値を実力に合わせて ±20 に広げた。

12treedump.py が .sites の出力パスを集計で上書きしていた

出力ファイルが黙って消える種類のバグ。

13学習に使えないデータを「測定用」と書いてあるツールが作る

luna-datagen --label は result（対局結果）を全サンプル0で書く。探索木から採った局面には周りに対局が無いため。そのまま学習に混ぜると「全部引き分け」として読まれ、しかもその歪みは尾部で最大になる。対策：RESULT_UNKNOWN の印を足し、そのサンプルだけ結果項を外した（エンジンは触っていない）。

14ベンチマークをファイルの先頭で取ってはいけない

先頭だけを測ると偏る。散らして測ること。ただし gen10 で続きがある：局面は散らしたが開始局面が50本しか無かったため、詰みの割合を7.5%と見積もって実測14.7%だった。散らすべき階層を間違えないこと。この事業のprobeは3回とも外していて、外し方は毎回「標本の取り方」である。
