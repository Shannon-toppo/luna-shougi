# 1層目を広げる — 値段は測れた、強さは測れなかった

2026年8月27日。`docs/nnue.md` のこの一文を検討した記録である。

> 小さめにしてあるのは意図的。1層目を広くするのが一番強くなる方向だが、メモリ帯域を全部そこで使うことになる。256でも手書き評価よりははっきり強い。

**結論を先に書く。値段は測れた。強さは測れなかった。**512次元のネットは学習に成功しながら drift ゲートを通れず、**一度も指していない。**

そして止まった理由のほうが、幅そのものより重い。**幅を倍にすると、この事業の量子化方式が前提にしているものが壊れる。**

> **8月27日、同日中に測れた。量子化を直したら通った(`docs/nnue-quantization.md`)。答えは「ほぼ差がない」である。**
>
> ```
> gen11-512 対 gen10-256   503 - 460 - 37   1000局 深さ6
>                          52.2%   Elo +14.9 +/- 21.2 (95%)   LOS 91.7%
> ```
>
> **信頼区間がゼロを含む。**95%では差を主張できない。LOS 91.7% なので「たぶん少し強い」までである。
>
> しかもこれは**深さ固定の対局で、1節で測った 0.86倍 NPS の代金を払っていない。**時計のある対局では、この +15 は速度の損で相殺される見込みが高い。**それは測っていない**(換算で言うのは規律5が禁じている手口である)。時間制の対局が要る。
>
> **`docs/nnue.md` の「1層目を広くするのが一番強くなる方向」は、この事業のこの規模では支持されない。**費用は 0.86倍 NPS、便益は測って +15±21。

## 1. 値段を測る — ゼロ詰めで一変数にする

上の一文は3世代にわたって書かれていたが、**誰も測っていなかった。**

素朴にやると一変数にならない。512のネットと256のネットは別のネットなので、探索する木が違い、NPSの差に評価の質の差が混ざる。

**gen10の重みを512次元にゼロ詰めした `.nnue` を作って、512のバイナリに食わせた。**余った次元は ft 重み・バイアスとも0なので clipped ReLU 後も0、L1の該当列も0で、**評価値が完全に同一**になる(L1入力は `[自分512|相手512]` なので、相手ブロックの移動だけ手当てする)。

狙いどおりに効いた。`bench 9` はノード数・評価値・最善手が全位置で一致し、**違うのは時間だけ**になった。

```
                      時間    NPS    対256   ノード数
  256 x 32(現行)    2298ms  587k   1.000   1,349,448
  512 x 32           2670ms  505k   0.861   1,349,448
  256 x 64(L1出力)  2565ms  526k   0.896   1,349,448
```

3回ずつ、ばらつきは1%未満。8並列(対局と同じ使われ方)では 2726 → 3252ms、**0.838倍**。帯域の取り合いは実在するが、上乗せは3ポイントである。

**固定深さの測定ではこの値段はゼロとして出る。**時計が無いからだ。実戦換算では 12〜25 Elo の前払いで、1000局の誤差幅 ±21 と同程度。**だから盤上の判定は今の手順のまま成立するが、持ち時間対局に移った日にこの分を返す。**

## 2. `network.hpp` のコメントは間違っていた

分解すると、L1のMACが16,384増える分が +267ms、特徴変換器の蓄積器・ClippedRelu・メモリtrafficの分は差し引き **+105ms(約5%)** しかない。

**費用の主犯は密なL1の演算(約12%)であって、特徴変換器のメモリ帯域(約5%)ではない。**特徴変換器は差分更新されるので安い。「1層目にメモリ帯域を全部使う」という診断は、この規模では成り立たない。

L1出力を 32→64 にするだけで 0.90倍かかることがその証拠である。特徴変換器を一切触らずに、同じ16,384 MACを足しただけでほぼ同額になる。

`src/nnue/network.hpp` のコメントは実測値に書き換えた。

## 3. 学習側の値段

RTX 4070 Ti、batch 8192、forward+backward+両optimizer+clip:

| ft_dim | steps/s | 100k steps | パラメータ |
|---|---|---|---|
| 256 | 44.4 | 37.6分 | 32.1M |
| **512** | **22.1** | **75.5分** | 64.2M |
| 1024 | 3.6 | 7.6時間 | 128.5M |

256の44.4は `runs/gen10/log.jsonl` の実測44.6と一致するので、この台は信用できる。**1024は崖である**(VRAM圧)。この機械では512が上限と見てよい。

val損失はgen10を全区間で下回り、**過学習の折り返しは最後まで来なかった:**

**この節の数字を信用してはいけない。**同じ日に、val損失がこの帯域で符号ごと外れることが実証された(`docs/nnue-step-budget.md`)。ここに残してあるのは、当時これを「幅は当てにいっている」と読んだ記録としてである。

## 5. ゲートで止まった

```
gen11      (512, 100k)   drift -22.9   FAILED(閾値 ±20)
gen11-long (512, 200k)   drift -40.9   FAILED
```

規律2に従って対局させていない。同じ日に作った256のネット5本は全部通っている:

```
gen10 -15.0 / gen10-long +4.5 / s25 +8.6 / s50 +7.9 / s150 +3.0
```

**幅で綺麗に割れた。**しかも512は step を増やすほど悪化する(-22.9 → -40.9)。

## 6. 犯人を3つ潰した

| 疑い | 検証 | 結果 |
|---|---|---|
| エンジンのバグ | `verify.py` 3000局面 | **完全一致** — シロ |
| int16蓄積器の溢れ | 最大 1,833 / 上限 32,767 | 18倍の余裕 — シロ |
| 補正の過学習 | 同一校正ファイルの別サンプル | -0.02 → +2.15 で転移 — シロ |

int16の溢れは筋の良い仮説だった。gen11の `max|d|` は1638でgen10の565の3倍、最悪局面は持ち駒10歩のような極端なものが並んでいた。`quantize.accumulate` がint32で計算してコメントに「エンジンのint16蓄積器が溢れたら verify.py で不一致として現れるように」と書いてあるとおり、**この事業はこの事態を予期していた。**測ったら溢れていなかった。

## 7. 真因 — 丸め誤差はもう定数ではない

`docs/nnue.md` はこう書いている。

> L1とL2は密で、**どの局面でも全入力を使う**。だから丸め誤差は「局面によってほとんど動かない活性ベクトル」に対する固定の線形汎関数、つまりほぼ定数になる。

**この前提が幅とともに壊れる。**

|  | 素の量子化誤差 平均 | **sd** | 補正後 平均 | **sd** |
|---|---|---|---|---|
| gen10 (256) | +66.5 | **114** | +1.4 | **90** |
| gen11 (512) | +11.6 | **386** | +2.2 | **248** |

**gen11の補正前のずれは +8.0 で、gen10の +64.4 より小さい。**壊れているのは平均ではなく広がりのほうである。L1の入力が1024個になり、独立な丸め誤差の和が √2 より大きく広がる(重みの大きさは両者ほぼ同じ、sd 0.065)。

補正は当てた集合の上では厳密にゼロにできる。**広がりは直せない。**だから他のどの分布でも外れる:

| 局面集合 | gen10 (256) | gen11 (512) |
|---|---|---|
| tree-gen2(driftの標準集合) | -14.9 | -23.6 |
| pool7 chunk-00(**校正と同分布**) | **-1.3** | **-22.2** |
| holdout6 | -12.9 | -36.8 |
| gen3-slice | -8.1 | -19.4 |

gen10は校正分布で -1.3 と正しく転移する。**gen11は自分の校正分布ですら -22.2 になる。**

**これは閾値の問題ではない。**±20 を緩めれば gen11 は通るが、通したものは「未測定の手番ボーナスを全ノードに撒くネット」のままである。規律7の換算(1点 ≒ 1.8 Elo)で -22.9 は約41 Elo に相当する。

## 8. 副産物 — int8の目盛りが1.7bit余っている

幅とは独立の発見である。L1重みの実際の大きさ:

| | max \|L1重み\| | 表現上限 (127/64) | 余裕 |
|---|---|---|---|
| gen10 (256) | 0.644 | 1.984 | 3.1倍 |
| gen11 (512) | 0.562 | 1.984 | 3.5倍 |

**両方とも上限の3分の1も使っていない。**`kWeightScaleBits` を 6 → 7 にすれば刻みが半分になり、丸め誤差も半分になる(上限0.992で両方収まる)。256側も良くなる。

**やっていない。**ファイルの意味が変わる変更で、既存の全ネットが黙って誤読されるため、`kFileVersion` を上げて全 checkpoint から再エクスポートする必要がある。判断が要る。

> **8月27日、同日中に実施。この節は二か所で間違っている。**`docs/nnue-quantization.md` に記録した。
>
> **(1) 一律 6→7 は実行できない。**この節はL1しか見ていない。43本の checkpoint を調べると **L2は28本で上限(1.9844)に張り付いている。**上限を半分にすればそのL2は切り落とされ、再エクスポートでは戻らず全部再学習になる。L1は目盛りが粗すぎ、L2は細かすぎて足りない — **一つの定数で両方は満たせない。**実施したのは層ごとの目盛り(L1だけ128、L2は64のまま)である。
>
> **(2) `kFileVersion` を上げる必要はなかった。**ヘッダのオフセット28が `reserved, 0` として空いていたので、そこに目盛り世代を入れた。**過去のファイルは全部そこがゼロなので、自動的に「世代0」を名乗って今までどおり読める。**バージョンを上げていたら、docs/ に結果が書いてあるネットが全部読めなくなっていた。
>
> 効果は予測より大きかった。gen11の素の量子化誤差sdが **306 → 72(4.2倍)**。刻み半分は2倍の効果を予測するので、**この差は説明できていない。**

## 9. 何が残っているか

**幅の問いは開いたままである。**gen11とgen11-longの checkpoint は `runs/` に無傷で、**再エクスポートとゲートは30秒**。量子化の方針が決まればすぐ測れる。

規律7が「**測定を見てから補正元を選ばない**」と明示しているので、**gen11が通る校正集合は探していない。**それは gen6 で名指しされた誤りそのものである。

選択肢は3つあり、どれも判断を要する。

1. **量子化を直す**(`kWeightScaleBits` 6→7)。根本的で256側も良くなる。形式変更
2. **閾値を実力に合わせる**。規律7は ±8 → ±20 で一度これをやっている。緩めるぶんは未測定の手番ボーナスとして飲む
3. **規律7の後段を使う** — 「この幅より小さい差を直接対決で主張するときは、両者の定数ずれを引き比べる」。ただしゲート自体は絶対値で切っているので、これは解釈の規則であって迂回にはならない

> **8月27日、同日中に選択肢1を実施。gen11はゲートを通った。**
>
> | 局面集合 | 世代0 | 世代1 |
> |---|---|---|
> | tree-gen2(**標準集合**) | **-25.2 FAILED** | **+6.7 PASS** |
> | tree-pool7 | -9.7 | -12.4 |
> | holdout6 | -39.1 | +8.7 |
> | gen3-slice | -20.6 | +1.6 |
>
> **閾値は緩めていない**(選択肢2は使っていない)。±20 のまま通った。校正集合も探していない — 世代0と世代1は同じ校正手順・同じ集合で、変えたのはL1の目盛りだけである。
>
> **通ったあとの盤上の結果は、この文書の冒頭に追記した。**drift はネットが自分のモデルからずれていないことしか言わない。

## 道具の変更

一本のツリーから両方の幅がビルドできるようにした。**追加のみ、既定の挙動は不変。**

- `src/nnue/network.hpp` — `kTransformedDim` を `LUNA_TRANSFORMED_DIM` で上書き可能に(既定256)
- `CMakeLists.txt` — `cmake -B build-wide -DLUNA_TRANSFORMED_DIM=512`
- `training/train.py` — `--ft-dim`(structural扱い、checkpointに載る)
- `training/checkpoint.py` — `build_model()` が checkpoint 自身の args から形を復元する。`ft_dim` の無い古い checkpoint は既定256として扱う
- `training/serialize.py` / `drift.py` — 既定値ではなく checkpoint の形を使う

パッチ後に256を再ビルドして `bench 9` を取り、**1,349,448ノードで以前と完全一致**することを確認してある。define は何も変えていない。

## 罠15 — 幅の違うバイナリは、間違ったネットを黙って受け入れる

512のバイナリに256のファイルを渡すと、理由を言って**手書き評価に落ちる:**

```
info string EvalFile failed: nets/gen10.nnue: wrong transformed dimensions:
  file has 256, engine was built for 512
info string eval hand-written
```

`ReadFrom` は正しく拒否している。問題は `luna-match` がこれを見ないことである。**パスを1文字間違えるだけで、1000局まるごと「対手書き」を測ってしまう。**

対策は、対局の前に両側のエンジンに実際にネットを読ませて `eval nnue` が返ることを確認すること。規律3(`info string eval nnue` の確認)を自動化するだけだが、**幅が2つになった時点でこれは必須になる。**幅は compile-time なので、比較は必ず2つの実行ファイルで行うことになるからだ。
