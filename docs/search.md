# 探索(フェーズ6)

フェーズ3で入れた alpha-beta + 置換表 + ムーブオーダリングに、枝刈りとマルチスレッドを足した。ここに書くのは「何を入れたか」より「なぜそれで正しいことになっているのか」と「どう測ったか」。

枝刈りは全部、**間違えることがある**。間違えたときに壊れるのが正しさではなく強さだ、という一点だけで許されている。だから採用の基準は「理屈が通ること」ではなく「自己対局で勝ち越すこと」になる。

## 測り方

`bench` コマンドを足した。6局面を固定深さで探索してノード数と時間を出す。

```bash
echo "bench 10" | ./build-msvc/Release/luna-shougi.exe
```

同じバイナリなら毎回同じノード数が出る。これが効いていて、**枝刈りを入れてノード数が動かなければそれは動いていない**し、**全局面で最善手が変わるなら枝刈り以上のことをしている**。局面は自己対局から取った。持ち駒の多い2局面が本番で、stand-patだけの静止探索が爆発するのはそこだけだからだ。

局面ごとに置換表を空にしてから探索するので、順番を変えても数字は変わらない。**1スレッドのときだけ意味のある数字**で、Lazy SMPは走るたびに違うノード数と違う時間を出す(どのくらい違うかは後述)。

強さの測定は `docs/measuring.md` の `luna-match`。ノード数は速くなったことしか言わない。

npsは150万から85万に落ちている。内部ノードで静的評価を呼ぶようになり、SEEも回すからで、これは枝刈りの代金として想定どおり。**1ノードあたりは遅くなり、必要なノード数が2桁減った**。

フェーズ5で深さ6にかかっていた52秒で、いまは深さ10以上に届く。自己対局では 200ms/手、200局で **+456.1 ± 101.6 Elo (LOS 100%)**。

## 静止探索の枝刈り

フェーズ5の時点で、深さ3の1局面に35万ノードかかることがあった(平手初期局面は2,472ノード)。持ち駒が多いと取り合いの木が指数的に広がる。教師データ生成の速度がこれで決まっていたので、ここが最優先だった。

### SEE(静的交換評価)

`src/search/see.cpp`。ある升で取り合いが起きたときに、手番側が最終的にいくら得をするかを、探索せずに数える。

実装は swap-off list。升から8方向にレイを引き、各方向の**手前の駒だけ**が攻撃側候補になる。手前の駒を使い切ったらレイを1つ進める。これで「香の後ろの香」「飛車の後ろの飛車」が正しく数に入る。桂馬は飛び越えるので遮蔽も開放もされず、最初に列挙して固定。

近似であることを承知で切り捨てたもの:

- **その升のことしか見ない**。取り返しが別の場所で駒をタダで置いていっても分からない
- **取り返しでは成らない**。成りを入れると手生成が要るし、符号が変わる筋はまれ
- **ピンされた駒も守り駒として数える**。1駒ごとに合法性判定を足す価値はない

玉だけ特別扱いする。玉は最も高いので「最も安い攻撃駒」に選ばれるのは他に何もないときだけで、そのとき相手にまだ攻撃駒があれば取れない(非合法)。そこで打ち切る。

### delta pruning

その手で取れる駒と成りの得を全部足しても、まだ alpha に余裕をもって届かないなら読まない。余裕(`kDeltaMargin`)は歩1枚ぶん。駒得だけが局面の価値ではないので、ぴったりで切ると読み落とす。

### SEE < 0 の取りを捨てる

**これが一番効く**。持ち駒が多い局面では、損な取り合いを始める手が持ち駒の数だけ存在し、その1つ1つが木を1段深くする。王手されている局面では適用しない。そこでの手は得をするために指しているのではなく、玉が逃げるために指しているからだ。

## 本探索の枝刈り

順番は探索コードに現れる順。

| 枝刈り | 条件 | 考え方 |
|---|---|---|
| PVS | 2手目以降 | 最善手はもう見つかっているという賭け。ゼロ幅で「これより良くない」ことだけ確かめ、外れたら読み直す |
| reverse futility | 深さ6以下 | beta より 190×深さ 以上高い。この残り深さで取り返せる差ではない |
| null move | 深さ2以上 | 相手にただで1手渡してもまだ beta を超えるなら、この局面は読むまでもない |
| futility | 深さ6以下の静かな手 | 静的評価が alpha より 180×深さ 以上低い。駒を取らない手で埋まる差ではない |
| late move pruning | 深さ6以下の静かな手 | オーダリングを信じて、規定数より後ろの静かな手を捨てる |
| SEE 枝刈り | 深さ6以下の取り | 深さに比例した額より損な取りは読まない |
| LMR | 深さ3以上、4手目以降の静かな手 | 浅く読んで alpha を超えなければそれで確定。超えたら読み直す |

静的評価に基づく枝刈りは、**PV上・王手中・詰みスコアが絡む窓では一切やらない**。PVではスコアそのものを使うので当て推量では困るし、王手中は「静かにしていれば」という前提が成り立たない。詰みが絡む窓では駒得のマージンが何も意味しない。

もう1つの決まりごととして、**1手も読み終えていないうちは何も枝刈りしない**。全部刈ったノードは `-kInfinite` を返し、それは詰みと読めてしまう。

### null move と将棋

将棋にはツークツワンクがほぼ無い。取った駒が持ち駒として戻ってくるので、「指せる手が全部自分の首を絞める」局面が成立しにくい。だから「1手パスしてもまだ勝っている」は素直に「読むまでもなく勝っている」の証拠になる。チェスの終盤で null move が危ないのとは事情が違う。

王手中はやらない。ただの1手が「玉を取る」になってしまう。連続でパスするのも禁止(`null_ok`)。2回パスは何も証明しない。

null move が返した詰みスコアは詰みではない。相手にただで1手あげて得た詰みなので、beta を超えたという事実だけ使って `beta` を返す。

`Position::DoNullMove` は手番とZobristキーだけを触り、**指し手履歴には積まない**。NNUEの差分計算は履歴を再生して「何が動いたか」を出すので、駒が動かない手が履歴にあると話がややこしくなる。積まなければ、null move の下で指された手は null move が無かったときと同じ形で履歴に並ぶ。千日手判定も、盤面が同じで手番だけ違う局面はキーが違うので誤検出しない。

### LMR の削減量

`0.75 + log(深さ) × log(手数) / 2.25` を切り捨てた表。深いノードほど、リストの後ろほど大きく削る。PVノードでは1減らす。削って alpha を超えたら、そのぶんを戻して読み直す。

## Lazy SMP

`--threads N` ではなく USI の `setoption name Threads value N`。

各スレッドが**同じ局面を最初から最後まで自分で探索する**。木を分割して配らない。共有するのは置換表だけで、それ以外(局面のコピー、指し手スタック、killer、history、ノード数)は全部スレッドごとに持つ。あるスレッドが早く証明したことは置換表に載り、他のスレッドはそこに歩いて行って探索を省く。

これが「怠惰(lazy)」と呼ばれる理由は、並列化の設計を何もしていないからだ。本当の並列探索より効率は悪い。代わりにコード量が桁違いに少なく、デバッグ不能な競合が入りにくい。この規模のエンジンはだいたいこれを選ぶ。

多様性の作り方は、ヘルパースレッドの反復深化を `1 + (id % 3)` 深さから始めること。それとスレッドのタイミングのばらつき。同じ深さに違う順番で到達するほど、置換表に載る情報の種類が増える。

止め方は素朴で、**メインスレッド(id 0)が終わったら探索は終わり**。ヘルパーは置換表を育てるために居るので、その後に見つけたものは使い道がない。返す手もメインスレッドのもの。スレッド間で投票するエンジンもあるが、ここではやっていない。

### 置換表

エントリを64ビット1語に詰め直した。ロックは取らない代わりに、**読み手が別々のエントリの断片を混ぜて読むことが原理的に起きない**ようにする。

```
bits 48-63  Zobristキーの上位16ビット
bits 32-47  指し手
bits 16-31  評価値
bits  8-15  深さ
bits  0-7   世代(上位6) + Bound(下位2)
```

キーの照合が32ビットから16ビットに減った。衝突の検出力は落ちるが、代わりにエントリが12バイトから8バイトになり、同じMB数でエントリ数が増えた。書き込み同士の競合は起こるままで、負けたほうは上書きされて消える。消えて困るものは何も無い(もう一度探索すれば出てくる)。

### 実測、および `bench` では測れないこと

`bench 10` の壁時計時間。7800X3D(8コア16スレッド)、各7回の中央値。

| スレッド | 中央値 | 最小 | 最大 | 対1スレッド |
|---|---|---|---|---|
| 1 | 3804ms | 3794 | 3806 | 1.00x |
| 2 | 3067ms | 3002 | 3203 | 1.24x |
| 4 | 2571ms | 2125 | 3286 | 1.48x |
| 8 | 2340ms | 1307 | 3694 | 1.63x |
| 16 | 2552ms | 1741 | 2694 | 1.49x |

**この表は速度の指標としてあてにならない**。1スレッドは7回で±0.3%に収まるのに、8スレッドは1307msから3694msまで3倍近く散らばる。ヘルパーが必要な局面を必要な順番で置換表に入れてくれるかどうかが運だからで、固定深さの短い探索6局面ではその運が均されない。中央値の1.63xも、最小の2.9xも、どちらも同じくらい本当ではない。

**実際の強さは自己対局で測る**。8スレッド対1スレッド、300ms/手、100局で **+172.8 ± 75.6 Elo (LOS 100%)**。誤差幅を大きく超えているので、スレッドが効いていること自体は確実に言える。倍率で語れる精度は無い。

このとき `--concurrency 1` は必須。並列対局にすると、機械が埋まったときに損をするのは8スレッド側だけになる。

16スレッドが8スレッドより速くならないのは物理コアが8つしかないから。SMTは探索のようにメモリ待ちの少ない処理では効きにくい。

ヘルパーは、指定された深さに達しても止まらず `kMaxDepth` まで進み続ける。メインスレッドが一番長い最終反復を回している間にヘルパーが引退すると、そのぶんのコアが遊ぶからだ。**この判断は理屈であって実測ではない**。上の表の散らばりでは、入れる前と後の差(中央値2446ms対2340ms)は区別がつかなかった。時間制限のある実戦では `max_depth` が64なので、そもそもこの分岐は踏まれない。

## 探索スレッドと stop

フェーズ5まで、探索はUSIコマンドハンドラの中で走っていた。探索中は入力を読まないので `stop` は届かず、`go infinite` は30秒で打ち切る細工でごまかしていた。

フェーズ6で探索を自前のスレッドに出した。結果として:

- `stop` が効く。実測で、無限探索を止めて `bestmove` が出るまで5ms

  ここで1つバグを踏んだ。`Think` が入口で停止フラグを消していたので、**`go` の直後に届いた `stop` が消えて探索が永久に走り続けた**。探索スレッドが `Think` に到達する前に `stop` が来る、という順番が普通に起こる。手で試したときは1.5秒待ってから `stop` を送っていたので気づかず、`go infinite` と `stop` を続けて流し込むテストで初めて止まらなくなった。フラグを消すのは出口(と、探索スレッドを作る前の呼び出し側)に移した
- `go infinite` が本当に無限になった。時間の上限は無い
- `isready` が探索中でも即答する。GUIはこれで生存確認をするので、黙るとエンジンが死んだと判断される
- 走っている探索の足元を崩すコマンド(`position`、`setoption`、`usinewgame`、`gameover`、`quit`)は、先に探索を止める

`ponder` はまだ。`USI_Ponder` を宣言していないのでGUIは送ってこない。スレッドはもう有るので、やるなら次はここ。

`UsiEngine::HandleCommand` を単体で使う経路(テストがそう)では、`go` は今も同期的に振る舞う。出力の受け取り先が無いところに後から `bestmove` を届けても誰も読まないからで、`Run` が出力シンクを付けているかどうかで分岐している。

## パラメータ

マージンや深さの上限は、チェスのエンジンで一般的な値を、この評価関数の単位(歩=盤上90、取ると190)に合わせて置いただけ。1つずつ動かして測り直す価値はまだ残っている。

やるなら `docs/measuring.md` の手順で、1つ動かすたびに400局。誤差幅より小さい改善は測れていないので、そこだけ守れば順番は好きにしていい。
