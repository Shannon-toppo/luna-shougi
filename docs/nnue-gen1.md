# 第1世代NNUEの記録 — 深さ4で作って、負けた

2026年8月10日。`docs/nnue.md` の手順を最初から最後まで1周回した記録。結果は**失敗**で、gen1は手書き評価に固定深さ6で 1-399-0(0.3%)。

失敗そのものより、**測定を4回間違えたこと**のほうが記録する価値がある。どれも例外を出さず、もっともらしい数字を返してきた。同じ罠は次の世代でも同じ形で待っている。

## 結論から

深さ4の自己対局データでNNUEを作ってはいけない。

深さ4の探索スコアは手書き評価そのものとほとんど同じ量なので、それを蒸留しても手に入るのは**手書き評価の劣化コピー**でしかない。そこに実行コストが乗る以上、勝てる道理がない。ラベルが手書き評価より多くの情報を持つ深さ — 6以上 — から始めること。

## 何を回したか

| | |
|---|---|
| データ生成 | `--games 20000 --depth 4 --concurrency 16`、約1時間、**235万局面**(197MB) |
| 学習 | `--steps 400000`(既定)、バッチ8192、RTX 4070 Ti で約2時間、57 steps/s |
| エポック数 | **1393**(40万step × 8192 ÷ 235万) |
| 訓練loss | 0.0402 → **0.0000435** |
| 量子化検証 | 5000局面で完全一致(AVX2) |
| 強さ | 固定深さ6・400局で **1 - 399 - 0**、Elo -800(下限に張り付き) |

`--steps 400000` は既定値だが、`docs/nnue.md` が想定していた1000万局面向けの数字だった。235万局面に対しては1393エポックになる。

## 測定の罠

### 1. EvalFileの読み込み失敗は「互角」という顔で返ってくる

最初に `--movetime 200` で400局回して 47.8%(Elo -15.6 ± 33.5)を得た。**この対局はNNUEを使っていない。**

エンジンは `EvalFile` の読み込みに失敗すると、`info string` で理由を言って手書き評価のまま対局を続ける。これはGUIのパス打ち間違いで対局そのものを失わないための設計で、正しい。ただし測定に使うと、**失敗した測定が「手書き評価 対 手書き評価」= 50% という、いかにも「有意差なし」に見える結果になる。**

対策: `luna-match` の出力に `info string eval nnue ...` が出ていることを毎回確認する。

### 2. bashのバックスラッシュ

失敗の原因はこれだった。

```bash
--option EvalFile=D:\Program\git\luna-shougi\nets\gen1.nnue   # 壊れる
```

引用符の無いバックスラッシュはbashがエスケープとして食う。エンジンに届くのは `D:Programgitluna-shouginetsgen1.nnue`。スラッシュ区切りで書けば起きない。

```bash
--option EvalFile=D:/Program/git/luna-shougi/nets/gen1.nnue   # 正しい
```

同じ理由で `bench` の比較も1度目は無効だった。**見分け方はノード数**で、深さを固定したベンチのノード数が両者で1ノードも違わないなら、それは同じ評価関数を2回測っている。

### 3. `eval` コマンドの出力は評価関数によって形が違う

```
info string eval material 123 pst -45 king 0 tempo 30 total 108   # 手書き
info string eval nnue -137 net D:\...\gen1.nnue (avx2)            # NNUE
```

「4番目のトークンを取る」と書くと、手書き側からは `material` の値が出てくる。**`material` は先手視点、`total` は手番視点**(`src/search/eval.cpp` の `terms.total`)なので、これを混ぜると先手番と後手番で相関が +0.807 / -0.807 に割れる。手番の符号バグが入っているようにしか見えないが、単に違う数字を比べている。

### 4. 訓練データの局面で汎化を測っていた

未知局面での挙動を見るつもりで `data/gen1.sfen` を使った。これは学習に使った局面そのものなので、何を測っても「暗記できているか」しか分からない。

別シードで生成し直したホールドアウトが要る。

```bash
./build-msvc/Release/luna-datagen.exe --out data/holdout.bin --sfen-out data/holdout.sfen --games 60 --depth 4 --seed 999 --concurrency 8
```

### 5. 検証lossは学習と同じ目標で測る

損失が最適化しているのは `0.7 × スコア勝率 + 0.3 × 勝敗`(`--lambda-score` 既定0.7)であって、スコア勝率だけではない。スコア勝率だけと比べると検証lossが0.016と出て、訓練lossの360倍に見える。正しい目標で測ると0.000219、5倍に収まる。**過学習の有無について正反対の結論が出る。**

## 測定結果

未知局面800(seed 999)で、各評価が教師ラベル(深さ4の探索スコア、手番視点)をどれだけ当てられるか。

| | ラベルとの相関 | 残差sd | 訓練loss | 検証loss |
|---|---|---|---|---|
| 手書き評価(静的) | +0.933 | **475** | — | — |
| gen1 (40万step, 1393エポック) | +0.894 | 583 | 0.0000435 | 0.000219 |
| gen1-short (3万step, 104エポック) | +0.894 | 581 | 0.000325 | 0.001042 |

読み方は2つ。

**ステップ数は原因ではない。** 過学習を疑って3万stepで回し直したところ、検証lossは5倍**悪化**した。1393エポックは多すぎるように見えるが、実際には長く回したほうが汎化していた。

**ネットワークは自分の教師より下手。** 手書き評価の残差sdが475、NNUEはどちらも583。深さ4の探索スコアを、その探索を駆動した手書き評価自身より正確には予測できていない。ステップ数を変えても動かない。ここが失敗の本体。

### 実行コスト

`bench 8`(両方ともパスが正しく通った状態):

| | ノード数 | 時間 | NPS |
|---|---|---|---|
| 手書き | 580,060 | 559 ms | 1,037,674 |
| NNUE | 1,107,545 | 1,831 ms | 604,885 |

コストが2つ重なる。**NPSが0.58倍**(評価1回が重い)、そして**同じ深さに着くまでのノード数が1.91倍**。合わせて深さ8への到達時間が**3.3倍**になる。

ノード数のほうが重要で、これは速度ではなく評価値の性質の話。評価が局面ごとにギザギザだとalpha-betaが枝を切れない。残差sd 583(歩=90なので約6.5歩)がそのまま効いている。フェーズ6の枝刈りマージンが手書き評価のスケールで調整されている影響もあり得る。

## なぜ深さ4では駄目なのか

深さ4の探索スコアは、手書き評価を4手先まで伝播させたものにすぎない。手書き評価との相関が高いのは当たり前で、そこには**静的評価が表現できない情報がほとんど含まれていない**。

蒸留で得られるものの上限は教師のラベルであり、その上限自体が「手書き評価とほぼ同じ」なら、うまくいっても引き分けが天井になる。そこに3.3倍の実行コストが乗るので、実際には大きく負ける。

`docs/nnue.md` の「手書き評価の間違いを覚えるだけになりやすい」という記述は、外部棋譜を使う理由として書かれていた。フェーズ6で探索が強くなったので第1世代も自己対局でよいと判断したが、**その判断が成立するのは深さを上げた場合だけ**だった。深さ4を選んだのは生成時間を6時間に収めるためで、そこが誤り。

## 積み残し

- **`training/train.py` に検証lossが無い**。この記録の数字は全部あとから外で測ったもので、学習中のログからは何も分からなかった。訓練lossだけが1000分の1に落ちていくのを見て「成功した」と読める状態になっている。ホールドアウトを切って `--log-every` ごとに出すべき。
- `uv run python -m training.verify --help` が日本語WindowsのCP932コンソールで `UnicodeEncodeError`(ヘルプ文字列中の全角ダッシュ)。実行自体には影響しない。
