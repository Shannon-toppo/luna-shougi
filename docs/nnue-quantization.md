# L1を独自の目盛りに移す — 量子化誤差の「広がり」を半分にする

2026年8月27日。`docs/nnue-width.md` の8節と9節が「判断が要る」として残した量子化の修正を、実際に入れた記録である。

**結論を先に書く。8節が提案した修正はそのままでは実行できず、実行できる形に直したところ、gen11 は drift ゲートを通った(-25.2 → +6.7)。**512次元のネットはこれで初めて盤に出て、**1000局で 52.2%、Elo +14.9 ± 21.2 だった — 区間はゼロを含む。**

つまりこの文書には結果が三つある。**量子化の修正は効いた。幅は効かなかった。そして修正が効いても step 曲線は説明できなかった。**

## 1. 提案されていた修正は、半分しか見ていなかった

`nnue-width.md` 8節はこう書いていた — L1重みは上限の3分の1しか使っていないので、`kWeightScaleBits` を 6 → 7 にすれば丸め誤差が半分になる、と。

**L1しか見ていなかった。**43本の checkpoint を全部調べたところ、L2は正反対だった。

| | max \|L1重み\| | max \|L2重み\| | 上限 (127/64) |
|---|---|---|---|
| gen10 | 0.6444 | **1.9844** | 1.9844 |
| gen11 | 0.5620 | **1.9842** | 1.9844 |
| gen7 | 0.8221 | **1.9844** | 1.9844 |

**43本中28本でL2が上限に張り付いている。**`kWeightScaleBits` を一律に上げれば上限は 0.9922 に半分になり、その28本のL2は切り落とされる。再エクスポートでは復元できず、全部再学習になる。

**L1は目盛りが粗すぎ、L2は細かすぎて足りない。**一つの定数で両方は満たせない。

## 2. 実行した形 — 層ごとの目盛り

L1だけを 128 に移し、L2は 64 のままにした。

```
                  重み    バイアス   シフト
  世代0  L1        64       8128       6
         L2        64       8128       6
  世代1  L1       128      16256       7      <- ここだけ
         L2        64       8128       6
```

活性は両世代とも `float × 127` の uint8 で、L1の積は `float² × 127 × 128 = float × 16256`、7ビット右シフトで `float × 127` に戻る。**出力層と特徴変換器は一切変えていない。**

L1の新上限は 127/128 = 0.9922 で、現行世代の実測 max\|L1\| は 0.32〜0.72。**全部収まる。再学習は不要。**

## 3. バージョンは上げなかった — ヘッダの予備語を使う

8節は「`kFileVersion` を上げて全 checkpoint から再エクスポートする必要がある」と書いていた。**その必要はなかった。**

ヘッダのオフセット28は `reserved, 0` として空いていた。ここに「目盛り世代」を入れると、**過去に書かれたファイルは全部そこがゼロなので、自動的に「世代0」を名乗る。**

```
  0   8   "LUNANNUE"
  8   4   version              (1のまま)
  ...
  28  4   scale generation     (旧: reserved, 0)
```

バージョンを上げていたら、新しいエンジンは `nets/` の既存ネットを全部拒否していた。**docs/ に対局結果が書いてあるファイルが読めなくなる**、つまり比較が一つ失われるということで、それは払う必要のない代金だった。

L1のシフトは compile-time 定数ではなく、ファイルから読んだ世代で `kL1WeightScaleBits[]` を引く。32個の値をレジスタにある数でシフトするだけで、bench に差は出ない。

## 4. 効いた — 広がりが落ちた

`nnue-width.md` 7節の診断は「**壊れているのは平均ではなく広がりのほう**」だった。校正は当てた集合の上では平均をゼロにできるが、広がりは直せないので他の分布で外れる、と。

同じ集合(mix30-v2 から4,096局面、校正と同分布)で測り直した。**世代0と世代1を一回の実行で並べて測っている** — 7節の表(256で114、512で386)は同じ量の別サンプルなので、そちらとこちらを引き算してはいけない。

| | | 素の平均 | **素のsd** | 補正後平均 | **補正後sd** |
|---|---|---|---|---|---|
| gen10 (256) | 世代0 | +62.0 | **97.0** | -0.0 | **79.5** |
| | **世代1** | +34.4 | **54.2** | -0.0 | **44.5** |
| gen11 (512) | 世代0 | -13.9 | **306.1** | -0.0 | **208.6** |
| | **世代1** | -62.4 | **72.3** | -0.0 | **64.8** |

**gen11の素のsdが 306 → 72 に落ちた。4.2倍である。**補正後も 209 → 65 で 3.2倍。

幅による広がりの罰は、**3.15倍から1.33倍に縮んだ**(世代0では gen11/gen10 = 306/97、世代1では 72/54)。

**なぜ2倍以上効いたのかは説明できていない。**刻みを半分にすれば各丸め誤差は半分、その和のsdも半分 — これは2倍の効果を予測する。4.2倍は予測より大きい。測っただけで、機序は分かっていない。

## 5. ゲートを通った

drift(量子化ネット対 float モデル、閾値 ±20)を、同じネット・同じ局面集合で世代0と世代1について測った。gen11、512バイナリ、engine で採点。

| 局面集合 | 世代0 | 世代1 |
|---|---|---|
| tree-gen2(**driftの標準集合**) | **-25.2 FAILED** | **+6.7 PASS** |
| tree-pool7 | -9.7 | -12.4 |
| holdout6 | -39.1 | +8.7 |
| gen3-slice | -20.6 | +1.6 |

**4集合中3つで大きく改善し、標準集合でゲートを通った。**tree-pool7 だけわずかに悪化している(-9.7 → -12.4)が、どちらも閾値の内側である。

256側も良くなっている(engine 対 float、holdout6、2,000局面):

| ネット | 世代0 | 世代1 |
|---|---|---|
| gen10 | -11.6 (sd 50.4) | **+3.6 (sd 33.3)** |
| gen10-s3125 | -12.0 (sd 40.5) | **+3.1 (sd 30.0)** |
| gen11 | -39.1 (sd 53.3) | **+8.7 (sd 43.8)** |

**再エクスポート時のクリップはゼロ。**3本とも警告なしで世代1に収まった。

## 6. 解禁された測定 — 幅はほぼ効かなかった

ゲートが通ったので、`nnue-width.md` が測れずに終わった対局を実施した。**両方とも世代1で再エクスポート**していて、違うのは幅だけである(幅は compile-time なので、2つの実行ファイルで走らせる。罠15のとおり、対局前に両側で `info string eval nnue` が返ることを確認した)。

```
gen11-512 対 gen10-256   503 - 460 - 37 (W-L-D)   1000局 深さ6
                         52.2%   Elo +14.9 +/- 21.2 (95%)   LOS 91.7%
```

**信頼区間がゼロを含む。**95%では「512のほうが強い」と言えない。LOS 91.7% なので、方向としてはたぶん少し強い、までである。

そして**この対局は深さ固定なので、幅の代金を一切払っていない。**`nnue-width.md` 1節の実測では512は **0.86倍 NPS**(8並列で0.84倍)である。時計のある対局ではその分だけ浅く読むことになる。

**+15 が速度の損で消えるかどうかは、測っていない。**NPSからEloへの換算で言うことはできる — が、それは規律5が「手書き評価を物差しにするな」で禁じている、道具をまたいだ連鎖そのものである。**時間制の直接対決が要る。**

言えるのはここまでである。**`docs/nnue.md` の「1層目を広くするのが一番強くなる方向」は、この規模では支持されなかった。**費用 0.86倍NPS に対し、便益は深さ固定で +15±21。

## 7. 壊していないことの確認

**世代0の算術が変わっていないことが、この変更で一番確かめるべきことだった。**変わっていれば docs/ に書いてある全部の対局結果が、静かに別のネットのものになる。

- **変更前のバイナリとの照合。**`dist/luna-shougi.exe`(この変更より前のリリース)と新ビルドに `nets/gen10.nnue`(世代0)を読ませ、holdout6 の3,000局面を採点。**0局面が不一致**
- **verify(engine 対 numpy、完全一致)。**世代0のランダムネット、世代1のランダムネット、再エクスポートした3本(gen10-g1 / gen10-s3125-g1 / gen11-g1、各2,000局面)、**全部完全一致**
- **単体テスト 170件、304,140アサーション通過**

C++テストに一本足した。**重みとバイアスを2倍にして1ビット多くシフトするのは、int32 の全値について厳密に同じ算術である**(`(2x) >> 7 == x >> 6`)。だから世代0のネットと、その重みを倍にした世代1のネットは、**同じ点数を返さなければならない** — エンジンがシフトをファイルではなくビルドから取っていたら、返せない。同じ数字を世代0として読むと点数が変わることも確かめている(そうでなければ、たまたま目盛りが効かないネットでもテストが通ってしまう)。

CIには世代0の verify を足した。**既定は世代1になったので、放っておくと世代0の算術は誰も動かさなくなる。**そこを間違えると `nets/` の既存ネット全部が黙って別の点数になる。

## 8. 変えたもの

**追加のみ。既定のファイル読み込み挙動は、既存ファイルについて不変。**

- `src/nnue/network.hpp` — `kL1WeightScaleBits[]`、`kCurrentScaleGeneration`、`Weights::scale_generation`(既定0)
- `src/nnue/network.cpp` — `Clamp8` がシフトを引数に取る。`ReadFrom` が世代を読んで検証し、知らない世代は拒否する。`WriteTo` が書く
- `training/quantize.py` — `L1_WEIGHT_SCALE_BITS`、`QuantizedNet.scale_generation` とその目盛りのプロパティ。`quantize(model, scale_generation)`
- `training/model.py` — `HIDDEN_WEIGHT_LIMIT` を `L1_WEIGHT_LIMIT` / `L2_WEIGHT_LIMIT` に分割。**両方 quantize.py の定数から導出**していて、書き写していない
- `training/serialize.py` — `--scale-generation`。古い checkpoint を世代0で出すための逃げ道
- `training/verify.py` — `--scale-generation`。世代0も検査できる
- `.github/workflows/ci.yml` — 世代0の verify を Windows と macOS の両方に追加

`train.py` は既定で世代1を書く。`model.py` のクリップ上限も世代1のものなので、**これから学習するネットは最初から世代1の目盛りに合わせて訓練される。**

## 9. 立てた予測 — 量子化誤差は step 曲線の一因か

この修正の値打ちは「gen11の測定を解禁する」だけではない。`docs/nnue-step-budget.md` が説明できずに残した山 — 学習を短く切ったほうが強い — の候補要因の一つが、**学習とともに3.3倍に育つ量子化誤差**だった。

```
   step   量子化誤差sd   対手書き
    781         27.5      51.9%
   3125         75.3      64.0%   <- 山
  12500         81.0      45.0%
 100000         90.1      27.4%
```

**相関はあるが因果は示せていない**(s1562 は誤差36.9で60.9%、s3125 は誤差75.3で64.0% — 誤差が倍でも成績は上)。単調に増える誤差と単峰の成績曲線は、二つの力の積に見える。

修正が効いたなら**山は右に動き、高くなるはずである。**これは検証できる予測で、step予算の曲線を世代1で引き直せば答えが出る。

## 10. 予測を検証した — 当たったが、説明にはならなかった

対手書きで曲線を引き直す代わりに、**各step予算で世代0と世代1を直接対決させた。**同じ重み・同じ幅・同じバイナリで、違うのは量子化の目盛りだけという完全な一変数比較である(世代0を読めるようにしておいたから測れる。3節の判断がここで効いた)。

**対局を見る前に、sd の改善比から予測を書き留めた。**

| step | sd改善比 (g0/g1) | 予測 | **実測 g1 対 g0** | ±95% |
|---:|---:|---|---:|---:|
| 195 | 1.03 | 0 | **+0.9** | 33.7 |
| 390 | 1.07 | 0 | **+12.2** | 33.0 |
| 781 | 1.09 | 0 | **−8.7** | 32.9 |
| 1562 | 0.93 | 0 | **−7.8** | 32.1 |
| 3125 | **1.85** | 大きく勝つ | **−0.9** | 31.8 |
| 6250 | 1.36 | 勝つ | **+11.3** | 32.3 |
| 12500 | 1.15 | 勝つ | **+14.8** | 32.1 |
| 25000 | 1.65 | 勝つ | **+40.1** | 32.8 |
| 100000 | **1.79** | 大きく勝つ | **+6.9** | 32.0 |
| 200000 | 1.57 | 勝つ | **+19.1** | 32.1 |

**予測1(低予算では効かない)は当たった。**1562以下をまとめると 742-746-112、1,600局で **Elo −0.9 ± 16.4**。ゼロである。

**予測2(高予算では勝つ)も当たった。**3125以上をまとめると 1115-1010-275、2,400局で **Elo +15.2 ± 13.1**。区間はゼロを含まない。個別に有意なのは 25000(+40.1、LOS 99.2%)だけだが、**まとめれば分離する。**

**予測3(効きの順は sd比 の順)は外れた。**順位相関は **+0.32** しかない。一番はっきりした外れは **step 3125 で、sd改善比は全点中最大の 1.85 なのに、盤上は −0.9 — 完全にゼロである。**100000 は比 1.79 で +6.9。

### これは step 曲線の説明にならない

修正の値打ちは高予算側で **+15 Elo** である。一方 step 予算そのものの効果は、同じ直接対決の物差しで **gen10 → gen10-long が −109 Elo**(`nnue-step-budget.md`)。

**量子化誤差は、step 曲線の力の1割程度しか説明できない。**9節の仮説は「実在するが小さい」で決着した。**学習を短く切ったほうが強い理由は、依然として分かっていない。**

目標指標のほうも動いていない。山の頂点を対手書きで測り直すと:

```
s3125 世代1 対 手書き   245 - 137 - 18   400局   63.5%   Elo +96.2 +/- 34.6
s3125 世代0(記録)                              64.0%
```

**山は高くならなかった。**sd が 68.8 → 37.1 と半分近く落ちても、である。

**予測を先に書いておいたことが、この結果を読めるものにした。**後から見れば「高予算で +15」は量子化仮説の支持に見えるし、「3125 でゼロ」は例外に見える。先に順序まで書いてあったので、**当たった部分と外れた部分を分けて数えられた。**

## 11. 残っていること — L2の天井

**L2の天井は直していない。**43本中28本が上限に張り付いているという事実は、int8@64 が L2 が欲しがるものを持てていないという意味である。これは定数の付け替えではなく設計の問題で、選択肢は(a)L2をもっと粗い目盛りにする(誤差は増える)、(b)L2をint16にする、(c)チャネルごとの目盛り。**別の実験にすべきで、いま混ぜると一変数にならない。**

## 罠17 — 目盛りの世代は、対局相手を選ぶ理由にはならない

世代0と世代1は同じバイナリが両方読める。だから `gen10.nnue` と `gen10-g1.nnue` は**直接対決できる** — 同じ重み、同じ幅、違うのは量子化の目盛りだけという、きれいな一変数の比較である。

**それが測れるのは、バージョンを上げなかったからである。**上げていたら、この比較は存在しなかった。

同時に、規律7の警告がそのまま効く。**測定を見てから世代を選んではいけない。**古い checkpoint を世代1で出してクリップ警告が出たら、それは「世代0で出せ」という意味であって、「クリップを見なかったことにする」という意味ではない。`quantize.quantize` がクリップ数を返し、`serialize.py` が警告を出すのは、その判断を人に見せるためである。
