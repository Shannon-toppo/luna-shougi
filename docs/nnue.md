# NNUE評価関数の作り方

フェーズ5で入ったもの一式の手順書。データを作り、学習し、量子化し、C++側と一致していることを確かめ、強くなったかを測るところまで。

学習は任意のタイミングで止められる。止めた続きから再開すると、止めずに回した場合と**ビット単位で同じ重み**になる。理由と仕組みは「止める・再開する」の節に書いた。

## 全体像

```
luna-datagen  →  .bin (教師局面)  →  training.train  →  checkpoint.pt
                                          ↓
                                     .nnue (量子化済み)
                                          ↓
                              training.verify で C++ と突き合わせ
                                          ↓
                              luna-match で前の版とレート比較
```

C++側は `src/nnue/` の5ファイル。Python側は `training/`。両方が同じネットワークを別々に計算していて、`training/verify.py` がその2つを1点も違わないことを確かめる。

## Python環境

uvが管理する。`pyproject.toml` と `uv.lock` がリポジトリに入っているので、初回は同期するだけでいい。

```bash
uv sync
```

以降、Python側のコマンドはすべて `uv run` を頭に付ける。

```bash
uv run python -m training.train --run runs/gen1 --data data/gen1.bin
```

**torchはPyPIから来ない**。CUDA版のtorchはPyTorch自身のインデックスにしか無く、どのインデックスを引くかがバイナリの積んでいるCUDAを決める。`pyproject.toml` は `cu132` を指していて、これは学習機のドライバ(RTX 4070 Ti、CUDA 13.2)に合わせたもの。ドライバを変えたらその1行を書き換えて `uv lock` を回し直す。

CUDAが効いているかは、走らせる前に一度見ておくこと。**効いていなくてもエラーにはならず、ただCPUで遅く回るだけ**なので気づきにくい。

```bash
uv run python -c "import torch; print(torch.__version__, torch.cuda.is_available())"
```

`2.13.0+cu132 True` のように、バージョンに `+cuXXX` が付いていて `True` が出れば正しい。`+cpu` と出たらCPU版が入っている。

CIはtorchを入れていない。`training/verify.py` はnumpyだけで動くようにしてあり、CIが要るのはそこまでだからだ。1.8GBのwheelを毎push落とす理由はない。

## アーキテクチャ

HalfKP → 256×2 → 512 → 32 → 32 → 1。

- **特徴量**: HalfKP。「自玉のマス」×「玉以外の駒がどこにあるか」の組。駒の表現はBonaPiece(1548種)で、盤上の駒は種類ごとに81マス分、持ち駒は1枚ごとに1つのスロットを使う。玉は入らない — 取られないし持ち駒にもならないし、玉の位置はもうKの側に入っているため。だから**どの局面でも常にちょうど38個**の特徴が立つ(40枚 − 玉2枚)。
- **入力次元**: 81 × 1548 = 125388。特徴変換器の重みだけで125388 × 256 × 2バイト ≈ 64MB。`.nnue` ファイルのサイズはほぼこれ。
- **手番**: 512次元の前半が手番側、後半が相手側。これがネットワークに手番を伝える唯一の経路なので、C++とPythonで順序が食い違うと静かに壊れる。

小さめにしてあるのは意図的。1層目を広くするのが一番強くなる方向だが、メモリ帯域を全部そこで使うことになる。256でも手書き評価よりははっきり強い。

## 量子化

学習は float、対局は整数。両者が完全に一致していないと、「学習中に測った強さ」と「実際に指すネットワークの強さ」が別物になる。

| 層 | 重み | バイアス | 出力 |
|---|---|---|---|
| 特徴変換器 | int16, スケール127 | int16, スケール127 | clipped ReLU で [0,127] の uint8 |
| L1 (512→32), L2 (32→32) | int8, スケール64 | int32, スケール8128 | int32を6bit右シフトして [0,127] |
| 出力層 (32→1) | int8, スケール9600/127 | int32, スケール9600 | 16で割ってエンジンの点数 |

ネットワークが学習するのは「点数÷600」に相当する量(600はポナンザ定数)。16で割ると歩=90のこのエンジンの単位になる。

int8にスケール64を掛けると表現できるのは ±127/64 ≈ ±1.98 まで。だから**学習中に毎ステップ重みをクリップする**(`model.clip_weights`)。学習後にクリップすると、ネットワークがその重みで覚えたことが丸ごと失われる。

`.nnue` のバイナリ形式は `src/nnue/network.hpp` の冒頭に書いてある。ヘッダに次元が入っていて、エンジンのビルドと違う形のファイルは読まずに理由を言って断る。

## 1. 教師データを作る

```bash
./build-msvc/Release/luna-datagen.exe --out data/gen1.bin --sfen-out data/gen1.sfen --games 20000 --depth 6 --concurrency 8 --stop-file data/stop
```

自己対局してその探索結果を記録する。USIパイプを介さずプロセス内で対局するので `luna-match` より速い。審判は `luna_match` のものをそのまま使うので、終局条件は測定用の対局と同じ。

- `--depth N` — 1手あたりの深さ。深いほど教師の質は上がるが局面数は減る。最初は6程度
- `--nodes N` — 1手あたりのノード数上限。**`--depth` と同時に効き、先に来たほうで打ち切る。既定で2,000,000が入っている**
- `--sfen-out FILE` — 全局面のSFEN。`training/verify.py` がこれをエンジンに投げ返す
- `--eval-file PATH` — NNUEで生成する。2世代目以降はこれを使う
- `--append` — 既存ファイルに足す
- `--stop-file PATH` / Ctrl+C — 進行中の対局を終わらせて止める。`--append` で続きから

記録しない局面: 王手がかかっている局面、詰みスコアが出た局面、`--score-limit`(既定3000)を超えた局面。どれも静的評価の教師としては意味が薄いか、出力レンジを引っ張るだけになる。

1サンプル84バイト固定。10M局面で約840MB。**固定長なのが重要**で、これのおかげでN番目のサンプルへのシークが掛け算1回になり、止めた学習を「データのどこまで読んだか」まで含めて再開できる。

### ノード数上限が既定で入っている理由

深さを固定しても仕事量は固定されない。フェーズ5の時点では静止探索に stand-pat 以外の枝刈りがなく、持ち駒が多い中盤局面では取り合いの木が爆発していた。**深さ3で、平手初期局面が2,472ノードなのに対し、持ち駒の多い中盤局面は354,629ノード**(482ms、seldepth 29 — 水平線の26手先まで潜っている)。

これを放置すると1局面で数分持っていかれる。実測で、`--depth 3 --maxply 100` の1局が68秒かかっていたのが、既定の200万ノード上限で10.6秒になった。

上限を入れても再現性は保たれる。ある局面をある深さで探索したときのノード数は、どの機械でも同じだからだ。1スレッドで走らせている限りは今もそうで、datagenがスレッドごとに `Search` を1つ持つのはそのためでもある。

フェーズ6で delta pruning とSEE枝刈りが入り、爆発そのものは無くなった(`docs/search.md`)。それでも上限は残してある。深さと仕事量が比例しないという性質自体は変わっていないし、生成時間の見積もりが立つほうが実用的だからだ。ただし既定の200万はもう緩すぎるので、実際には `--depth` を上げて `--nodes` はそのままにするのが今の使い方になる。

### floodgateの棋譜から始める場合

自分の手書き評価が指した対局だけで学習したネットワークは、その手書き評価の間違いを覚えるだけになりやすい。最初の1世代だけ人間や強いエンジンの棋譜を使う手がある。

```bash
uv run python -m training.csa_to_data --out data/floodgate.bin --sfen-out data/floodgate.sfen wdoor2024/*.csa
```

ただしCSA棋譜には**局面ごとの評価値がない**。スコアは0で書かれるので、このデータは `--lambda-score 0`(勝敗のみ)で学習すること。datagenのデータと1つの学習に混ぜてはいけない。

## 2. 学習する

```bash
uv run python -m training.train --run runs/gen1 --data data/gen1.bin --steps 400000 --export nets/gen1.nnue
```

主なオプション:

- `--batch-size` (既定8192)、`--lr` (既定1e-3)
- `--lambda-score` (既定0.7) — 探索スコアと勝敗のどちらを信じるか。1.0で探索スコアのみ、0.0で勝敗のみ。最初の世代はスコア寄りでないとそもそも学習が進まない(1局の勝敗はラベルとして雑すぎる)。逆に勝敗寄りにしていくと、教えた探索より強くなる余地が出る
- `--save-every` (既定2000) — チェックポイント間隔。1つ約385MB(重み128MB + Adamの状態256MB)なので、置き場所には注意
- `--export PATH` — チェックポイントのたびに `.nnue` も書く

損失は「予測勝率」と「探索スコアの勝率 と 実際の勝敗 を混ぜたもの」の二乗誤差。点数そのものではなく勝率で測るのは、+2000と+3000が指し手としてはほぼ同じ局面だから。その差を学習させるとネットワークの容量が無駄になる。

特徴変換器の勾配は疎(1バッチで触るのは1局面あたり38行だけ)なので、`EmbeddingBag(sparse=True)` と `SparseAdam` を使っている。密な勾配にすると、数千個の数字を変えるために毎ステップ32M個の重みを書き直すことになる。7800X3DのCPU上・小さいバッチでの実測で17倍。GPUでの比はこれとは違うはずだが、無駄な仕事であることは変わらない。

## 3. 止める・再開する

学習は何時間も回る。その間その機械は他のことにも使う。エポックの切れ目まで待つのも、プロセスを殺して1時間分捨てるのも嫌なので、**いつでも止めて、続きから再開できる**ようにしてある。

止め方は3通り、どれも同じところに着地する。

```bash
# 別のシェルから止める(現在のステップを終えてチェックポイントを書いて終了)
uv run python -m training.control runs/gen1 stop

# 一時停止。GPUは解放されるが、データのどこまで読んだかは保持したまま待つ
uv run python -m training.control runs/gen1 pause
uv run python -m training.control runs/gen1 resume

# 学習プロセスで Ctrl+C。stop と同じ。2回目の Ctrl+C はチェックポイントを諦めて即終了
```

再開:

```bash
uv run python -m training.train --run runs/gen1 --resume
```

`--resume` は引数をチェックポイントから全部読むので、実行ディレクトリだけ渡せばいい。一緒に渡した引数はそちらが優先されるので、学習率やステップ数を途中で変えるのもこれでできる。

### なぜファイルで制御しているか

学習機はWindowsで、WindowsにはSIGUSR1もなければ、あるプロセスに任意のシグネルを送る手段もない。ファイルなら両OSで同じように動き、テキストエディタでも作れる。ファイルは `runs/<名前>/control/` に置かれる。

### 「続きから」の中身

重みだけ保存したチェックポイントは、ネットワークは残せても**学習は残せない**。次の1ステップが何をするかを決めているのは、Adamのモーメント、学習率スケジュール、データのどこを読んでいるか、乱数の状態の全部だからだ。これを落とすと、再開後は「同じ重みから始まる別の学習」になり、止めた前後をまたいだ測定に意味がなくなる。

なので保存するのはこれ全部:

- モデルの重み
- 2つのオプティマイザ(密/疎)とそれぞれのスケジューラの状態
- データローダの位置(エポック、チャンク、チャンク内のバッチ)
- Python / numpy / torch / CUDA の乱数状態

データの順序は「シード + エポック番号 + チャンク番号」から決まるようにしてあるので、位置は3つの整数で足りる。データを実際に何万バッチ読み飛ばす必要はない。

書き込みは一時ファイルに書いてから rename する。停止要求は保存中にも来るし、書きかけのチェックポイントは無いよりも悪い。

**確かめ方**: 40ステップ通しで回したものと、20ステップで止めて再開して40ステップにしたものの重みを比べる。全パラメータで差が完全に0になる。

```bash
uv run python -m training.train --run a --data data/gen1.bin --steps 40 --batch-size 64
uv run python -m training.train --run b --data data/gen1.bin --steps 20 --batch-size 64
uv run python -m training.train --run b --resume --steps 40
```

ここがずれる典型的な原因は「ループを抜ける前にバッチを1つ余計に取り出してしまう」こと。取り出した時点でデータローダの位置は進むので、チェックポイントは「学習していないバッチを学習済み」と記録し、再開した側はそれを飛ばす。`train.py` が停止条件を**バッチを取り出す前に**見ているのはこのため。

## 4. C++側と一致していることを確かめる

**このフェーズで一番大事な検証**。量子化のバグはクラッシュしない。エンジンが少し弱くなるだけで、学習側からもエンジン側からも単独では気づけない。

```bash
uv run python -m training.verify --engine build-msvc/Release/luna-shougi.exe --net nets/gen1.nnue --sfen data/gen1.sfen
```

同じ局面を両方に通して、点数が**完全に一致する**ことを見る。近い、ではなく一致。両方とも整数演算で、正当に丸めが違う余地はどこにもない。

学習済みネットワークがなくても走る:

```bash
uv run python -m training.verify --engine build-msvc/Release/luna-shougi.exe --random-net /tmp/x.nnue --sfen data/gen1.sfen
```

乱数で作ったネットワークを書き出して確かめる。検証しているのは算術と特徴量の番号付けであって学習結果ではないので、これで十分。CIが毎pushで回しているのはこちら。**macOSのCIジョブはNEONカーネルをこれで検証している** — 開発機がx86なので、NEONに対する自動テストはこれしかない。

`--sfen` を省くと `training/verify.py` に埋め込んだ数局面を使う。持ち駒あり・なし、成駒、玉が動いた局面、両方の手番が入っている。

## 5. エンジンで使う

```
setoption name EvalFile value D:\nets\gen1.nnue
```

ShogiGUI / ShogiHome のエンジン設定画面から設定できる。空にすると手書き評価に戻る。読み込みに失敗したときは `info string` で理由を言って手書き評価のまま続ける — GUIの設定にパスの打ち間違いがあったときに失うのは強さであって対局ではない。

現在どちらで評価しているかは `eval` コマンドで見られる(USI外の独自コマンド)。使っているSIMDカーネルも出る:

```
info string eval nnue -137 net D:\nets\gen1.nnue (avx2)
```

`(scalar)` と出たらAVX2が有効になっていない。x86では `-DLUNA_ENABLE_AVX2=ON`(既定)で `/arch:AVX2` が付く。

## 6. 強くなったか測る

`docs/measuring.md` の手順そのまま。同じバイナリ同士を、片方だけ `--option EvalFile=...` を付けて対局させれば、評価関数の差だけが測れる。

```bash
./build-msvc/Release/luna-match.exe \
  --engine ./build-msvc/Release/luna-shougi.exe --name nnue --option EvalFile=D:\nets\gen1.nnue \
  --engine ./build-msvc/Release/luna-shougi.exe --name handmade \
  --games 400 --movetime 200 --concurrency 8
```

そのあとは `--eval-file` を付けて次の世代のデータを作る、の繰り返し。

## 差分計算について

NNUEが速いのは、1手指しても特徴が2〜3個しか変わらないから。38行足し直す代わりに数行の加減算で済む。

`src/nnue/evaluate.cpp` がその管理をしている。アキュムレータは「その局面までに指した手数」で索引したスタックに置き、**Zobristキーで検証する**。手を戻して別の手を指すと古いエントリが残るが、キーが合わないので必ず弾かれる。正しさがキーの一致だけに依存しているので、探索の側に「ここでpushしろ」といった約束事が要らない。

玉が動いたときはその側の半分を作り直す。HalfKPの特徴は全部玉のマスで索引されているので、差分では済まない。作り直すには玉が動いた**後の**局面が要るので、玉の手は連鎖の最後の1手としてしか再生できない。`FindChainStart` が連鎖にそれ以外の玉の手が含まれていたら丸ごと諦めて全再構築に落とすのはこのため。

`Position::Undo` が指し手・取った駒に加えて「動いた駒」と「変化した持ち駒のスロット」を持っているのは、局面を復元せずに差分を計算できるようにするため。これがあると数手前のアキュムレータからでも再生できる。

## テスト

C++側 (`tests/test_nnue.cpp`, `ctest` で走る):

- BonaPieceの反転が対合であること、盤上の駒では色の入れ替えと180度回転になっていること
- どの局面でも特徴がちょうど38個であること(駒を取っても盤から持ち駒に移るだけなので変わらない)
- **局面とその先後反転(盤を180度回して駒の色を入れ替えたもの)が、反対側から見て同じ特徴集合になること**
- **SIMDカーネルがスカラー版と1ビットも違わないこと** — ネットワークが使う全部の形について
- ファイル形式の往復。壊れたファイル・途中で切れたファイルを読まずに断ること
- **差分更新したアキュムレータが、作り直したものと同じ点数を出すこと** — ランダムな240手の対局を通して。途中で手を戻して別の手を指し、古いエントリが残った状態も通る
- 玉の手を含む手順での同じ確認
- 玉がない局面で手書き評価に落ちること

Python↔C++は上の `training/verify.py`。CIが両OSで毎push実行する。

## 数字と目安

| もの | 大きさ |
|---|---|
| `.nnue` ファイル | 64MB |
| チェックポイント | 385MB (重み128MB + Adam 256MB) |
| 教師データ | 84バイト/局面 |
| 深さ6の自己対局 | 1局あたり数秒〜十数秒 |
