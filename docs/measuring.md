# 効果測定の手順

`luna-match` は2つのUSIエンジンを連続対局させ、勝率とレート差を出すツール。フェーズ4以降、探索や評価関数に手を入れたら必ずこれを通す。入れる前と入れた後を対局させて、レート差が誤差より大きいかを見る。

## なぜ自前で書いたか

将棋対応のマッチランナー(cutechessのようなもの)を持ってくると、ルール判定がエンジン本体と別実装になる。フェーズ1で2〜3週間かけた合法手生成と、審判の合法手生成が食い違うと、負けた理由がバグなのか弱さなのか分からなくなる。`luna-match` は審判に `luna_engine` をそのまま使うので、この食い違いが原理的に起きない。

## 比較対象のビルド

変更前のバイナリはgitのworktreeから作る。作業ツリーを汚さずに済む。

```bash
git worktree add /tmp/luna-before <比較したいコミット>
```

```bash
cmake -S /tmp/luna-before -B /tmp/luna-before-build -A x64 -DLUNA_BUILD_TESTS=OFF && cmake --build /tmp/luna-before-build --config Release --parallel
```

測定が終わったら `git worktree remove /tmp/luna-before` で片付ける。

## 実行

```bash
./build-msvc/Release/luna-match.exe --engine ./build-msvc/Release/luna-shougi.exe --name after --engine /tmp/luna-before-build/Release/luna-shougi.exe --name before --games 400 --movetime 200 --concurrency 8
```

`--help` に全オプションがある。よく使うのは以下。

- `--movetime MS` 1手固定時間。再現性が高く、短時間で回るので普段の測定はこれでいい
- `--byoyomi MS` / `--time MS` 実戦に近い時間管理まで含めて測りたいとき
- `--concurrency N` 並列対局数。7800X3Dなら8。物理コアを超えると1局あたりの実効速度が落ちて、時間管理の挙動まで変わってしまうので超えないこと
- `--games N` 偶数に切り上げられる。同じ開始局面を先後入れ替えて2局指すため
- `--record FILE` 全局を `position sfen ... moves ...` 形式で書き出す
- `--option NAME=VALUE` 片方のエンジンにだけ `EvalFile` を渡せば、NNUEと手書き評価の差だけが測れる

NNUE用の教師データは `luna-match` ではなく `luna-datagen` が作る。プロセス内で自己対局するぶん速い。手順は `docs/nnue.md`。

## 出力の読み方

```
after vs before: 301 - 97 - 2 (W-L-D), 400 games, 75.5%
Elo +195.5 +/- 39.8 (95%), LOS 100.0%
```

- `+/-` は95%信頼区間の片側幅。**レート差がこの幅より小さければ、その変更は測れていない**。勝ったように見えるだけ
- `LOS` は本当に強くなっている確率。95%を超えるまでは採用の判断をしない
- 誤差幅は対局数の平方根でしか縮まない。100局で±75なら、±25にするには900局要る。小さい改善を測るときは局数を覚悟する

## 前提と限界

- **開始局面はランダム**。平手初期局面から `--openings` 手(既定4手)をランダムな合法手で進めた局面から指す。決定的なエンジン同士を初期局面から指させると毎回同じ棋譜になり、100局が1局にしかならないため。片方に有利な開始局面を引く可能性はあるが、同じ開始局面を先後入れ替えて2局指すことで相殺している
- **千日手は4回目の同一局面で引き分け**。連続王手の千日手は王手をかけ続けた側の負けとして裁く
- **入玉宣言は27点法で検証する**。宣言が条件を満たしていなければ、宣言した側の負け
- `--maxply`(既定320手)を超えた対局は引き分けとして打ち切る
- 引き分けが多い条件ほど1局あたりの情報量は多い。誤差幅は実際に出た勝敗の散らばりから計算しているので、これは自動的に反映される

## 測定の記録

| 変更 | 条件 | 結果 |
|---|---|---|
| フェーズ4の評価関数(駒割のみ → 駒割 + PST + 玉の安全度 + 持ち駒ボーナス + 手番) | 200ms/手, 100局 (seed 1) | +151.3 ± 76.0 Elo, LOS 100% |
| 同上、別シードで確認 | 200ms/手, 400局 (seed 5000) | +195.5 ± 39.8 Elo, LOS 100% |
| フェーズ6の枝刈り一式(SEE、delta、null move、futility、LMP、LMR、PVS) | 200ms/手, 200局 (seed 1234), 8並列 | +456.1 ± 101.6 Elo, LOS 100% |
| Lazy SMP 8スレッド 対 1スレッド | 300ms/手, 100局 (seed 909), 1並列 | +172.8 ± 75.6 Elo, LOS 100% |
| 量子化のバイアス補正(gen1、補正あり 対 補正なし) | 200ms/手, 400局 (seed 4242), 8並列 | +62.3 ± 34.5 Elo, LOS 100% |
| 同上、別シードで確認 | 200ms/手, 400局 (seed 777), 8並列 | +40.1 ± 34.3 Elo, LOS 98.9% |

100局と400局で信頼区間が重なっているので、フェーズ4の2つは同じ結果を2回測っただけと見ていい。局数を4倍にして誤差幅がほぼ半分になっているのも、平方根で縮むという想定どおり。

フェーズ6の枝刈りは誤差幅を大きく超えている。93%勝ちなので誤差幅自体が広く出ているが、この大きさなら局数を増やして確かめる意味は薄い。**枝刈りが1つも入っていない探索に最初の一式を入れる**のは、それ以降の1つずつのチューニングとは桁が違う、という話でしかない。

### マルチスレッドを測るときの注意

`--concurrency` は**1にすること**。8スレッドのエンジンと1スレッドのエンジンを並列対局で比べると、機械が埋まったときに損をするのは8スレッド側だけで、測っているものが「スレッドの効果」ではなく「混雑の効果」になる。1局ずつ指させるので時間はかかる。
